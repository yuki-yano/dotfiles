# Apple HIG

Apple Human Interface Guidelines（HIG）を、プロダクトの設計、実装、監査へ適用する。

HIGはApple純正アプリの外観を複製するためのスタイル集ではない。
利用者の目的、操作の予測可能性、適応性、アクセシビリティ、細部の品質を判断する基準として扱う。

## 判断の優先順位

次の順で判断する。

1. ユーザーの明示的な指示
2. プロダクトの仕様と既存の振る舞い
3. 対象プラットフォームの制約とデザインシステム
4. 実行時に確認した現在のApple公式HIG
5. このskillの運用上の基準

HIGを理由に機能を追加したり、プロダクト固有の語彙をAppleの語彙へ置き換えたりしない。
仕様とHIGが衝突し、解決によってプロダクトの振る舞いが変わる場合は、根拠と影響を示してユーザーへ確認する。

## 共通準備

どのモードでも次を行う。

1. 対象リポジトリの`AGENTS.md`と`CLAUDE.md`を全文読み、適用範囲を確認する。
2. 対象ユーザー、主要タスク、対象画面、対象プラットフォーム、入力手段を特定する。
3. 仕様書、既存画面、デザイントークン、コンポーネント、参考画像を必要な範囲で調べる。
4. 画像はファイル名や説明だけで判断せず、実際に表示して確認する。
5. [HIGの共通評価基準](references/hig-baseline.md)を読み、対象に関係するApple公式ページを検索またはHTTP取得で確認する。

Apple公式ページの参照だけならブラウザUIを操作しない。
公式ページを取得できない場合は、未確認の内容を現行HIGとして断定しない。

## 作業モード

依頼に合うモードのreferenceだけを読む。

- 視覚的な仕様源がまだなく、新規UIや再設計の方向性をImageGenで決める場合は、[ImageGenによる方向性探索](references/ideation.md)を読む。
- ユーザーが承認した画像、モック、スクリーンショット、Figma frameを実装する場合は、[承認案の実装](references/implementation.md)を読む。
- 既存の画面やフローを評価、修正、定期点検する場合は、[既存UIの監査と改善](references/audit-and-improve.md)を読む。

監査と修正を同時に依頼された場合は、監査で証拠を揃えてから修正する。
方向性探索から実装までを一度に依頼された場合でも、ユーザーが生成案を選択する前に実装へ進まない。

モーション、ジェスチャー、spring、rubber-banding、material表現だけが対象なら`apple-design`を使う。
このskillから`apple-design`を併用するのは、それらが現在の作業範囲に含まれる場合に限る。

## 権限と変更範囲

- 監査やレビューだけを依頼された場合はファイルを変更しない。
- 実装や改善を依頼された場合も、対象画面と検証に必要な範囲だけを変更する。
- 既存のプロダクトロジック、情報構造、技術スタックを、デザイン上の都合だけで変更しない。
- ユーザーが明示しない限り、commit、push、deploy、外部サービスへの公開を行わない。
- 後方互換対応やfallbackを追加しない。必要になった場合は、必要性と影響を示してユーザーへ確認する。

## 停止条件

次の場合は推測で続行せず、確認できた事実と不足している情報を報告する。

- 必須の仕様源、画面、参考画像へアクセスできない。
- 参考画像を必要な生成または比較処理へ添付できない。
- 方向性探索でbuilt-in ImageGenを利用できない。
- 仕様源同士に、作業結果を変える未解決の矛盾がある。
- 既存UIの監査に必要な画面またはフローをキャプチャできない。
- 選択された生成画像を会話内の表示順から一意に特定できない。
- ユーザーが視覚案または必要なレスポンシブ一式をまだ承認していない。
- スクリーンショットだけでは検証できない事項について、適合を保証するよう求められている。

## 完了報告

参照したApple公式ページ、対象範囲、実施内容、検証結果、未確認事項、残課題を報告する。
設計書または計画書を作成した場合は、機能完了条件、テスト完了条件、運用反映条件から成る測定可能なDoDを含める。
