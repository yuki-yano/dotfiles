# 成果物の最終推敲

制作時の依頼文、修正の経緯、例示が成果物に混ざっていないか確認し、会話を知らない読者が単独で理解できる形に整える。
制約は成果物の設計に反映し、読者の理解・判断・操作に必要な情報は本文に残す。

## 適用範囲

- 公開記事、操作ガイド、説明資料、UIの文言など、第三者へ渡す成果物の最終確認・推敲に使う。過去に作成した成果物も対象にできる。
- 修正を重ねた成果物では、古い説明、継ぎ足した注記、用語や前提の不整合を通して点検する。軽微な修正ごとの必須工程にはしない。
- 設計書や引き継ぎ文書では、実装者・運用者を読者として判断する。実行指示や設計制約も、読者に必要なら本文に残す。
- 秘密情報の検出や技術的な正しさの検証を、この推敲だけで完了したと扱わない。

## 情報の扱い

対象読者と用途を、依頼内容と成果物から判断する。各記述は次の基準で扱う。

| 記述の役割 | 扱い |
| --- | --- |
| 読者の理解・判断・操作に必要な情報 | 本文に残す |
| 書き手への制作上の指示 | 構成、語彙、操作説明、例の選び方へ反映する |
| 会話の経緯や不要な制作事情 | 削除するか、読者に必要な内容へ書き直す |

「ご要望に合わせて」「前の案から変更して」「この制約を満たすために」などを手がかりにする。
語句だけで機械的に削除せず、その記述が読者に何を伝えているか判断する。
依頼中の例は意図を理解する材料として扱い、成果物の主題や要件に勝手に昇格させない。

## 保持する情報

- 対象範囲、適用条件、前提、出典、根拠、数値、引用、固有名詞、意味のある具体例。
- 事実・推定・未確定の区別、検証した範囲、未検証事項、既知の制限。
- 設計判断とその理由、決定済み事項、DoD、完了判定の根拠、実行権限や運用上の制約。
- 明示された構成・主張・文体・用語など、今回の変更対象に含まれないもの。

文を自然にするために、不確実な主張を断定へ変えたり、不足した根拠を補作したりしない。
説明が必要な前提や制約は、読者に伝わる形へ整えて残す。

判断例：

| 記述 | 判断 |
| --- | --- |
| UIの「初心者向けにするというご要望に対応しました」 | 利用者が行う操作や必要な補足へ書き直す |
| 記事の「CLIを使わないよう指示されたため」 | 採用した操作手順を直接説明する |
| 技術資料の「この値は推定で、移行後の実測ではない」 | 判断に必要な検証限界として残す |
| 引き継ぎ文書の「commit・push・deployは禁止」「運用反映条件」 | 実行範囲や完了条件として残す |

## 確認と編集

- 確認・レビューだけの依頼ではファイルを編集せず、該当箇所、理由、修正案を示す。
- 修正・推敲の依頼では、許可された成果物を編集する。目的、主張、機能、構成を依頼範囲外へ広げない。
- 文言だけでなく、見出し、注記、キャプション、用語、前提を通して確認する。制作事情を削った後も、読者が次の操作や判断に進めることを確かめる。

## 編集元と出力

- 既存の編集元と生成方式を守る。正本から生成されるHTML説明資料は、YAMLなどの編集元を修正して再生成する。HTML自体が正本の成果物は、そのHTMLを編集する。
- 変更の影響に応じて既存の形式検証や参照確認を行う。同じ差分で成功済みの検証は、新しい失敗や懸念がなければ繰り返さない。
- 修正済み本文を返す依頼では、本文を直接提示する。「指示の痕跡を除去しました」などの前置きを付けない。
- ファイルを編集した場合は、成果物へのリンク、変更の要点、実施した検証を簡潔に報告する。制作上の説明を成果物の本文へ混ぜない。
