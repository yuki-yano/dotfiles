このサービス層、DBアクセスと外部API呼び出しと業務ルールが1つのメソッドに同居していて、変更の影響範囲が読みづらくなっています。たとえば決済APIの仕様が変わると、注文サービスのテストまで書き直しになります。

提案は三つです。まず、DBアクセスはリポジトリ層に切り出します。次に、外部APIはクライアントクラスに閉じ込め、サービスからはインターフェース越しに呼びます。最後に、割引計算や在庫判定といった業務ルールだけをサービスに残します。

こうすると、サービスのテストはモックを差し替えるだけで済み、DBを立ち上げなくても回せます。外部APIがタイムアウトしたときのリトライも、クライアント側に集約できます。

一度に全部直すと差分が大きくなります。まずは外部API呼び出しの切り出しから始める形でどうでしょうか。ここは障害時の影響が一番大きく、効果も見えやすいと思います。
