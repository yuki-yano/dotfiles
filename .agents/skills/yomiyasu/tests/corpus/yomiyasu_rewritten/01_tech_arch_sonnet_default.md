非同期メッセージングキューを挟むと、マイクロサービス間の結合は疎になります。しかしキューを置いただけでは、耐障害性は得られません。

キューは At-least-once 配信を基本とするため、開発者は同じメッセージが複数回届く前提で設計します。コンシューマは冪等にし、メッセージIDを処理済みテーブルに記録して重複を排除します。

次に、処理に失敗したメッセージの扱いを決めます。即時に再試行すると障害中の下流サービスへさらに負荷がかかるため、指数バックオフにジッタを加えて再試行の間隔を空けます。規定回数を超えたメッセージは Dead Letter Queue へ移し、本流のキューが詰まらないようにします。DLQ にメッセージが溜まったら運用担当者へ通知し、原因を調べて再投入するところまでを運用として設計します。

送信側にも注意点があります。DB 更新とメッセージ発行を別々に行うと、片方だけ成功してデータが食い違ったままになります。更新と同じトランザクションでアウトボックステーブルに書き込み、別プロセスがそこからメッセージを発行するアウトボックスパターンを使えば、この食い違いを防げます。

最後に、キューに滞留しているメッセージ数と、最古のメッセージが滞留している時間を監視します。スループットの低下は、障害の最初の兆候として現れます。
