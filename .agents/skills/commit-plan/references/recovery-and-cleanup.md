# 失敗時の扱いとクリーンアップ

## 状態確認

失敗した操作、`git status --short`、`git diff --cached`、作成済みコミットを確認する。
commitの成否が不明なら、HEADとlogを確認してから再試行を判断する。

- 原因が依頼内のformat・検証失敗なら、対象の修正と必要な検証を行って再試行できる。
- 並行編集、計画との不一致、対象外の変更を伴う復旧は停止してユーザーに確認する。
- hookの無効化、ブランチ移動、commit取消、作業ツリーの巻き戻しを自動で行わない。

## ステージングの取り消し

自分が今回stageした差分だけを取り消せる。
ファイル全体を戻す場合は、開始前のstaged差分や他の作業が混ざっていないことを確認してから
`git restore --staged -- <file>`を使う。作業ツリーの内容は戻さない。
混在する場合は、保存済みpatchの逆適用で自分の差分だけを取り消す。

## クリーンアップ

成功時は、今回作成した`$commit_plan_dir`内のpatchだけを削除し、空になった今回のディレクトリを`rmdir`で消す。
失敗時は原因確認に必要なpatchを残し、その場所を報告する。
`.git/commit-plan`全体や、他の実行のバックアップをまとめて削除しない。

## 停止時の報告

失敗した操作と原因、作成済みcommit、残りのstaged / unstaged差分、
確認が必要な次の操作を示す。根拠のない再試行や破壊的な復旧を提案しない。
