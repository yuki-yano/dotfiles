# Release Flow

依頼されたリリースを、プロジェクトの方式に沿って準備・実行・公開状態の確認まで完了する。

## 方式と実行範囲

- プロジェクトに専用のリリースskillやscriptがあれば優先する。
- branch、remote、対象差分、公開先、version指定、CIのtriggerを確認する。設定ファイルの存在だけでdeploy方式を決めない。
- [方式別手順](references/release-methods.md)から、Web deploy、tag publish、ローカルpublish・個別方式の該当節を読む。
- 明示されたcommit・push・deploy・publishと、その完了に必要な既存手順を実行する。同じ範囲の承認を取り直さない。
- commit指示がなければcommitしない。意図別の分割が必要なら`commit-plan`を使う。
- versionを発行する依頼で指定も既存規約もなければpatchを既定とする。minor / majorは明示指示がある場合だけ使う。
- リリース用の新規ブランチを勝手に作らない。

## 公開前の検証

必要なci・build・pack検証は、最初のcommit・tag・push・公開操作より前に行う。
同じ差分・環境で成功済みの結果が確認できれば利用し、versionや生成物の変更で無効になった検証だけを追加する。

失敗中の成果物は公開しない。
原因が依頼内のコードや設定にある場合は、修正と影響する検証を行い、成功後に続ける。
対象外の修正、権限変更、公開先の判断が必要なら、それ以外の準備を終えたうえで確認する。

## 状態変更と失敗時の扱い

- 意図しない差分はユーザーに確認する。既に除外・保護が決まった差分を再確認しない。
- 操作結果とGit・公開先の状態を確認してから次へ進む。
- pushや公開の成否が不明な場合は、remote・workflow・registry等を読み取って確定するまで再送しない。
- 部分的に公開された、tagが衝突した、対象が想定と異なる場合は後続の状態変更を止め、到達状態と必要な判断を報告する。
- 権限・hook・検証の迂回や、別の公開方式への自動切替で通さない。

## 完了報告

コミットhash、公開先URLまたはversion、workflow結果、実施・再利用した検証を示す。
途中停止なら、完了済み操作と未完了操作を分け、現在の外部状態と次に必要な判断を伝える。
