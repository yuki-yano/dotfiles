# 画像と製品プレビュー

画像を使う場合だけ読む。スタイル方針を解除した項目は既存の設計に従う。ダッシュボードや設定画面では、通常は画像を追加せず、内容そのものを見せ場にする。

## 題材を決める

- 何を見せる画像か、なぜこの製品に必要かを一文で説明する。関係のない球体やロボットで埋めない。
- 製品プレビューなら、主張を裏付ける一つの操作や結果を見せる。予約なら実際の予約枠、コードレビューなら差分とコメントなど、既存の機能に基づく。
- 生成画像を使うLPでは、題材の場面をheroの背景に置き、文字を置く静かな領域と製品画面の位置を一体で構成する。背景画像が必要という理由だけで新しい機能を発明しない。
- プレビューは対象プロジェクトの部品で組み立てる。静的なモックと実際に操作できる画面を混同させない。
- 内容、表記、数値を揃える。同じ請求書を複数の場所へ見せるなら、顧客、番号、金額も同じにする。

## 表現を選ぶ

方向性の性格に合うものを一つ選ぶ。具体例は[完成見本](refs.md)で確認する。

| 表現 | 適する内容 |
| --- | --- |
| 空や風景を使った穏やかな背景画 | 温かさや人の活動に関係する製品 |
| 一つの実物を光で見せる写真 | 落ち着きや信頼感が必要な題材 |
| 柔らかな素材の小さな3D場面 | 遊び心や親しみが必要な題材 |
| カード、端末、荷物などの実物の描画 | 製品が実際に扱う物を示す箇所 |
| 光学や物理現象 | 現象と機能の関係を説明できる技術的な題材 |
| 単色の版画や印刷表現 | 書体やページ全体も同じ性格を持つ場合 |

文字や点で画像を描く処理、duotoneなどは、内容と結び付く場合だけ使う。例えば金額や請求書を扱う製品で数字を素材にする。一箇所の主要な画像に絞り、余計な装飾を増やさない。

画像加工を実装する場合、ピクセル取得は読み込み時にまとめ、毎frameで`getImageData`しない。静止画で目的を満たすならアニメーションを加えない。動かす場合は画面外で停止し、動きを減らす設定を尊重する。

## 画像生成が必要な場合

- 利用環境に既にある画像生成ツールと、その手順・権限条件に従う。既に許可された範囲の承認を取り直さない。未接続のサービスや依存を自動で追加しない。
- 題材、場面、光と配色、表現、構図、画像サイズを指定する。画像へ文字、ロゴ、ボタン、UIを焼き込まず、それらは実装側で扱う。
- 全体の背景なら、文字を置く側に静かな空間を残す。切り抜きが必要なら、用途に合う透過画像を生成する。
- 結果を一文の目的と配色に照らして判断する。闇雲に再生成せず、必要な修正をプロンプトへ反映する。
- 必要な画像生成が使えない場合は、その箇所を未完了として報告する。空の枠を完成した画像として扱わない。

## 配置と読み込み

- 画像はプロジェクトのassetとして保存し、一時URLへ依存させない。
- 必要に応じてWebPやAVIFを使い、表示サイズと端末の解像度に合う大きさにする。
- 意味のある画像には内容を伝える`alt`、装飾画像には空の`alt`を使う。
- 画像寸法を確保し、読み込みで画面が大きく動かないようにする。主画像の読み込み優先度は実際の表示位置に合わせる。
- 背景色や境界をページへなじませる。ただし製品写真の輪郭など、内容を理解する境界まで消さない。
- 生成した端末へ実際のUIを重ねる場合、画像に印刷された偽の文字で置き換えない。
