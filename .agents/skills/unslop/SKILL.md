# 既存UIの診断と仕上げ

Damir Sokolovsky（[@heydamir](https://x.com/heydamir)）による [unslop](https://github.com/heydamir/unslop) のローカル派生。本文・参照資料を日本語化し、日本語UIへの対応、スタイル方針の解除、既存の操作手段との統合を加えている。動画・サイト保存スクリプトは含めない。[CC BY 4.0](LICENSE) に基づき、複製・改変時も作者と出典を保持する。

画面の余白、配色、アイコン、文言、書体、レイアウト、細部、画像、動きを順に見直す。装飾を減らすだけで終えず、プロダクトの内容から、その画面で目立たせるものを決める。

## 変更しない条件

- 機能、情報、実データ、プロダクト名、セクションの順序を、見た目の都合で変更しない。数値の精度、単位、比較対象、系列の区別も保持する。
- 読みやすさ、キーボード操作、フォーカス表示、コントラスト、動きを減らす設定への対応を守る。以下のスタイル方針を解除しても、この条件は解除しない。
- 監査だけの依頼では編集しない。修正の依頼では対象画面と必要な検証に範囲を絞る。
- 画面確認は適用先のAGENTS.mdと利用環境のブラウザ選択順に従う。このskillを使うために依存や外部サービスを追加しない。

## スタイル方針の適用と解除

既定では、この本文と参照資料の強いスタイル方針を有効にする。中立色中心の配色、書体・太さの制限、チャートの主従、装飾の抑制も残す。

ユーザーは自然言語で、一括または項目別に解除できる。設定ファイルは作らない。

| 指示の例 | 扱い |
| --- | --- |
| 「配色と書体は維持して」 | 指定された配色と書体を保持し、そのほかの方針を適用する |
| 「チャート構成は変更しない」 | チャートの種類、数、配置、主従を保持する |
| 「独自スタイルの指定はすべて無効」 | 配色・書体・チャートに加え、アイコン、角丸、レイアウト、動きなどの好みの指定も解除する |
| 「余白と整列だけ直して」 | 修正をその範囲に絞る |

解除した項目は既存のデザインシステムや画面を基準にする。監査表や既定値と異なるだけでは問題とせず、実際の不統一や読みにくさを診断する。無効にした規則を最終チェックで再適用しない。

日本語UIへの対応と「変更しない条件」は常に適用する。開始時に、有効な方針と維持する項目を短く示す。既に分かる指示や承認は確認し直さない。

## 日本語UIへの対応

- 既存の和文フォントとコンポーネントを優先する。未選定ならOS標準の日本語表示を基準にし、欧文用フォントを選んだだけで和文の選定を終えない。書体の候補だけを理由にWebフォントを追加しない。
- 和文見出しへ欧文用の狭い行間や負の字間を機械的に当てない。文字サイズ、行間、太さは[既定値](references/tokens.md)を出発点に、漢字・かなが読めるかで判断する。
- 句読点・閉じ括弧の行頭、開き括弧の行末を避ける。本文を`word-break: break-all`で分断しない。長いURLや識別子の折り返しは、その要素で扱う。
- 操作ラベルの省略や固定幅で意味を失わせない。長い日本語、狭い画面、文字拡大での折り返し・欠けを確認する。
- 英文のsentence caseや大文字小文字の規則を和文へ持ち込まない。見出し・ボタンの句点は基本的に省き、説明文は自然な句読点で書く。
- 「検索」「変更を保存」など、操作や対象を具体的に書く。汎用キャッチコピー、根拠のない誇張、毎回の挨拶見出しを避ける。
- 同じ種類の数値は桁揃えと書式を統一する。ただし金額、割合、件数など異なる意味の精度まで一律にしない。「前月比+12%」のように比較対象を残す。

## 進め方

1. 対象画面、実装、既存のトークン・コンポーネントを確認する。画面を実行できる場合は表示を見て判断する。URLや画像だけが対象なら、再構築が依頼範囲に含まれるかを確かめ、成果物が実サイトの更新ではないことを明示する。
2. [診断項目](references/signs.md)から、適用中の方針に関係する問題を拾う。「場所・見えている問題・修正方針」を1行ずつ記録する。
3. 修正量を決める。問題が多ければ全体を調整し、少なければ見つかった箇所だけを直して既存ブランドを維持する。問題がなければ、その事実を伝えて無理に変更しない。
4. 全体を変える場合は、以下の5項目で方向性を短く示す。未承認の方向性が作業結果を左右する場合は案を示して回答を待つ。実行を任されている場合や、既に案が選ばれている場合は、その範囲で進める。局所修正では既存の方向性を使う。
5. 以下の9項目を順に点検・修正する。対象外・解除済みの項目は飛ばす。項目ごとに画面全体を整えるが、変更はまとめて実装してよい。
6. 診断で見つけた問題が解消したか確認する。画面確認は大きな変更の節目にまとめ、細かな修正ごとに繰り返さない。表示不具合や未解決事項があれば追加で確認する。
7. 変更内容、維持・解除した項目、検証した範囲と残課題を報告する。

### 方向性

- **プロダクト:** 何を、誰のために行う画面か。
- **性格:** 「落ち着いた、正確な、少し温かい」など具体的な2〜3語。「モダン」「洗練」「プレミアム」だけで済ませない。
- **題材:** 紙とインク、計測器など、内容に根拠がある場所や素材。色や画像の判断材料にする。
- **見せ場:** 内容が伝わるチャート、実データ、実物の写真など、色と細部を集める1〜2箇所。
- **固有の細部:** 開発ツールのキー表示など、操作や内容に関係する一つの細部。飾るために発明しない。

実在するブランドは維持する。既存ロゴやブランド色をAIっぽいと判断しただけで作り直さず、変更が依頼範囲に含まれるか確認する。

## 1. 余白

- 既存の良いスケールがあれば使い方を整える。未整理なら4px刻みを基本にし、小さな操作部品の微調整は2px、光学的な中央揃えは端数を許す。
- 同じ役割の行高、余白、カード内側の間隔を揃える。グループ内よりグループ間を広くする。
- アイコン、ラベル、右寄せの数値をそれぞれ同じ列に揃える。理由のない個別の位置補正を取り除く。
- ページ、カード、ナビゲーションの密度を分ける。具体値は[既定値](references/tokens.md)を使う。

## 2. 配色

- 背景、浮いた面、罫線、文字は一つの中立色の階調から選ぶ。アプリでは表面を無彩色に近づけ、題材の色はアクセントと内容へ集める。
- 文字色は主・副・補助の3役、操作部のアクセントは原則1色。意味を持つ状態色と、系列を区別する色は保持する。
- 色相をまたぐグラデーション、文字のグラデーション、発光、色付きの影、背景の光の塊を取り除く。同系の中立色内での小さな明暗変化はよい。
- 暗色では面の明度差と細い罫線、明色では小さな中立色の影で奥行きを作る。派手な装飾を別の流行へ置き換えない。
- 通常の文字は背景とのコントラスト比4.5:1以上を基準にする。アクセント上の文字、薄い補助文字、フォーカス表示も読みやすさを確認する。

## 3. アイコン

- 装飾用の絵文字は、導入済みの一つのアイコンセットか、不要なら無装飾にする。ユーザーの投稿やコンテンツとしての絵文字は削らない。
- サイズ、線幅、アイコン枠、ラベルまでの間隔を揃える。既存セットがなければ、まず必要なアイコンを既存手段で表現できるか確認する。
- 色は文字の役割に合わせる。意味のない色分けや、すべての見出しへのアイコン追加を避ける。

## 4. 文言

- 見出しは画面で扱う情報、操作、結果を具体的に示す。「作業をもっとスマートに」など他製品でも使える文言にしない。
- 「おかえりなさい！」よりページや対象期間を示す。短いラベル、感嘆符なし、不要な句点なしを既定にする。
- 検証できない実績や倍率を創作しない。確認できない主張は未確認として報告し、実際の意味や権利に関わる表示を勝手に削らない。
- モック用データは内容に合うものを使い、実データと混同させない。実データを見栄えのよい数値に置き換えない。
- `PRO`や`Beta`などの表示は、契約・利用条件・状態を伝える役割があるなら保持し、控えめに整える。

## 5. 書体

- UI用に1書体、必要なら数値・補助情報や大見出しにもう1書体まで。題材と性格から選び、既存ブランドの書体を維持する。
- 太さは400と500を中心にし、まれな強調だけ600を使う。700〜900の見出しや斜体による強調を避け、サイズと色で主従を作る。和文の可読性が不足する場合は調整する。
- 欧文ラベルはsentence caseを基本にし、意味のある略語・固有名詞の表記は保持する。小さい文字へ負の字間を使わない。
- 数値は必要に応じて`tabular-nums`で揃える。和文の補助ラベルまで機械的に欧文の等幅書体へ変えない。

## 6. レイアウト

- アプリは実際のデスクトップ画面として扱い、狭い中央カラムへ縮めない。ナビゲーションと本文の幅・密度を分ける。
- LPは、題材に合う場面と製品プレビュー、左右非対称の分割、大きな製品画面のいずれかを軸にする。場面画像は内容を説明できる場合に使う。
- 長い見出しは左揃えを基本にする。主操作は一つ、その隣の副操作は多くても一つにする。既存の必要な操作は削らず、優先順位や配置を調整する。
- 最初の画面を全体で構成し、無意味な空白を残さない。小画面では読み順に並べ、プレビューを単に縮小して文字を読めなくしない。実際の機能やデータを減らさない。

## 7. 細部とチャート

- 角丸は大きさと入れ子の関係で決め、すべてを同じ丸い形にしない。内側の角丸は外側から間隔を引く値を出発点にする。
- 件数は静かな文字、ショートカットはキー表示にする。選択状態は小さな面の明度差で示す。
- チャートは一つを主役にし、そのほかは小さなリストや表など異なる構成にする。同じ大きさのチャートを繰り返さず、余白と大きさに主従を付ける。
- 一つの系列を虹色にしない。重要な系列や時点だけを強調し、複数系列の区別に必要な色・凡例・ラベルは保持する。
- stat cardはラベル、数値、比較対象付きの変化を基本にし、穴埋めのsparkline、ミニバー、アイコンを足さない。既存の小グラフが判断に必要な情報を伝えるなら、削除せず配置や構成を調整する。
- 推移は線、比較は棒、割合は積み上げ棒や一覧、単一目標は進捗表示を出発点にする。データの意味に合わないチャートへ変えない。
- 同じデータの反射・複製を、別の系列や実際の比較データのように描かない。補助目盛りや数値を装飾として創作しない。

## 8. 画像と製品プレビュー

- 無関係な球体、宇宙、ロボット、発光する脳などの埋め草を除き、製品や実際の内容を見せる。
- アプリやダッシュボードでは、データ、写真、アバター、状態表示自体を見せ場にする。画像生成は必要な空状態、導入画面、マーケティングなどに絞る。
- 画像が必要な場合だけ[画像の指針](references/visuals.md)と[完成見本](references/refs.md)を読む。見本の構成原理を参考にし、題材やレイアウトを複製しない。
- 表示に必要な代替テキスト、画像寸法、読み込み時の安定性を守る。空の画像枠や未実装の製品画面を完成扱いしない。

## 9. 動き

- 実際の状態を示さない点滅、脈動、浮遊、過剰なパララックスを除く。操作への応答や変化の説明になる動きは残す。
- `transition-all`、カードの拡大hover、単純なUIの過度なバウンドを避ける。色、背景、罫線、透明度、transformなど対象を指定する。
- 大きなレイアウト値やぼかしを連続アニメーションさせない。少数の時間と一つのeasingを基本にし、読み込み演出は多くても一つにする。
- `prefers-reduced-motion`では移動・拡大・バウンドを減らし、状態が分かる静止表示や短い色・透明度の変化にする。解除した動きの好みを理由に、この対応を外さない。

## 最終確認

- 依頼範囲と解除条件を守り、機能・情報・データの意味を維持したか。
- 日本語の文字組み、長いラベル、小画面、文字拡大で欠けや意味の欠落がないか。
- 診断した余白・整列・書式の不統一が解消したか。
- 有効なスタイル方針に従い、不要な装飾を別の装飾へ置き換えていないか。
- フォーカス、キーボード操作、コントラスト、動きを減らす設定を保ったか。
- 全体調整の場合、製品名を他製品へ置き換えても成立するだけの画面になっていないか。局所修正に独自性のための改造を持ち込んでいないか。
- 未実施の検証や不足した画像などを、完了したと報告していないか。
