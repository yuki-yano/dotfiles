# Empirical Prompt Tuning

再利用する指示の発動範囲、判断の明瞭さ、実行結果を点検する。
通常の改訂は構造審査と編集で完結する。独立agentによる評価は、ユーザーが明示した場合だけ行う。

## モード選択

| 依頼 | 行うこと |
|---|---|
| 確認・レビュー・最適化の相談 | 構造審査と改善案 |
| 作成・修正・見直し | 構造審査、対象の編集、変更に応じた検証 |
| subagent評価・並列agent検証・empirical evaluation・バイアス排除読み | [実証評価手順](references/empirical-evaluation.md)を読み、独立シナリオを実行 |

修正依頼の途中で、評価未依頼を理由に編集を止めない。
一度限りの使い捨てプロンプトや、文章の好みだけの変更に評価工程を追加しない。

## 構造審査と編集

- descriptionの発動条件と本文の用途・成果物が一致しているか確認する。広すぎる発動条件や不要な言い換えを整理する。
- 明示された制約と、過去の失敗を補うための手順を区別する。削ることで壊れる具体的な操作契約は残す。
- 目的に不要な手順の固定、承認の取り直し、全資料の先読み、同じ検証の繰り返しを探す。
- 本文、参照先、既定プロンプトの矛盾を確認する。用途別の詳細は必要時だけ読む配置にする。
- 変更理由を実例や不明瞭点に結び付け、要件自体を都合よく緩めない。
- 形式validatorや参照リンクを確認し、スクリプト変更があれば影響する検証を実行する。

実証評価を行わない場合も、典型例と境界例で判断がどう変わるかを点検する。
この静的点検から、成功率や速度が改善したとは主張しない。

## 報告

変更点と根拠、静的に確認した範囲、未検証の挙動を簡潔に示す。
実証評価を行った場合だけ、固定シナリオごとの結果と未達要件を添える。
