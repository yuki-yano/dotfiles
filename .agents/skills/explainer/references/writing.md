# 速習資料の型

## 構成

```
# <読み手の問いの形のタイトル>

> 想定読者 / 省いたもの / 所要時間 / 検証方法（1 行ずつ）

## 0. 一枚で          ← 問いに答える表。本文を読まなくても持ち帰れる
## 1..n 本文         ← 表の各行を 1 節ずつ展開する。1 節に例は 1 つ
## n+1 チェックリスト  ← 読み手が明日から使う形（レビュー項目など）
## n+2 理解度チェック  ← 3〜5 問。答えは <details>
## 付録：再現         ← コマンド 3 行と、ファイルの表
```

## 文体

- 1 段落は 1〜2 文にする。長い説明は段落を分ける。
- 主張の直後に例を置く。例の直後に、その例から読み取ることを 1 文で書く。
- 太字は 1 節に 1 つまで。その節の結論に使う（「読みやすい日本語」）。
- 用語は、初出で 1 回だけ定義する（「CTI（帰納法の反例）」）。
- 書き手が確信を持てないことは、本文から外すか「未検証」と書く。ぼかした言い方で残さない。
- ペルソナの言語で書く。ペルソナ本人の文体（段落の長さ・語彙）に寄せる。

## 引用のマーク

検証スクリプトは、次のマークの直後のコードブロックを実物と照合する。

````markdown
<!-- output: z3-is-odd -->
```
x % 2 === 1: sat
```

<!-- source: examples/z3/01-is-odd.mjs -->
```js
const s = new Solver();
```
````

- `output:` の後には `checks.json` の `name` を書く。ブロックの各行が、実行結果に順に現れなければならない。長い出力は途中の行を省いてよい。
- `source:` の後にはファイルパスを書く。ブロックがファイルの連続した一部と一致しなければならない。

## 理解度チェックの作り方

- 各問いは、本文の「一枚で」の表の 1 行に対応させる。
- 「〜は何か」ではなく、判定を問う（「この緑で安心できない理由は？」）。
- 答えは 2〜3 文。本文のどの例で確かめられるかを書く。
- 誤答しやすい選択肢（「unsat なら実装は正しい」）を問いの形にする。

## 価値を先に、根拠は後に

読み手にとって何が変わるか（何を判定できるようになるか、何が直るか）を、最初の 2 節までに書く。
コード・出力・図は、その主張の根拠として後に置く。仕組みの説明から始めない。

書き終えたら、2 回消してみる（削除テスト）。

1. 根拠（例・出力・図）の節を全部消す。残った節だけで、伝えたいことが言えていなければ、主張が書けていない。
2. 主張（読み手にとって何が変わるか）の節を全部消す。それでも資料が成り立って見えるなら、それは根拠を読み上げているだけ。

伝えたいことの 1 文、節の役割の表、削除テスト、「依頼文にあった／推測した」の分け方は、[HyperFrames](https://github.com/heygen-com/hyperframes)（Apache-2.0）の `story-spine.md` と `brief-contract.md` を参考に、この資料向けに書き直した。

## 読みやすい日本語

書き終えたら、AI の文章に出やすい次の型を直す。チャットで説明するときも同じ。

| 型 | 直し方 |
|---|---|
| 太字が多い（1,000 字に 3 つ以上） | 太字は 1 節に 1 つ、その節の結論だけにする。箇条書きの頭を「- **判定**：…」のように太字のラベルにしない。ラベルが要るなら表にする |
| 箇条書きが多い（行の 4 分の 1 を超える） | 箇条書きは、並べても意味が変わらない項目だけにする。理由・順序・対比でつながる内容は、文でつなぐ |
| 文末のコロンで、次の箇条書きを導く（「見るもの：」） | 「見るものは次の 3 つ。」のように文で書くか、表にする。「日時：10 時」のようにラベルと値を区切るコロンは残す |
| 比喩の動詞（黙って無視する、倒す、潰す、効く） | 実際の動作で書く。「エラーを出さずに無視する」「優先する」「直す」「役に立つ」。何が起きるか分からないなら、元の語を残す |
| 飾りの否定（「A ではなく B」） | A と取り違えられやすいときだけ残す。そうでなければ B だけを書く |
| 役割に合わない大げさな名詞（契約、正本、台帳） | 実際の役割で書く。「ルール」「原文」「一覧」。正式な名前（vlmkit の check などの道具名）は変えない |
| 予告だけの文（「注目すべき点があります」） | 続く中身と 1 文にする |

直すときも、主張・言い切りの強さ・文の働き（説明か、依頼か、決まりか）は変えない。元にない情報を足さない。

[yomiyasu](https://github.com/nanaism/yomiyasu) が入っていれば、`verify-doc.mjs` が `yomiyasu_lint.py` で本文を点検し、見直す候補を △ で出す（落としはしない。人の文章でも点数が出るため）。
この節の型は、yomiyasu（MIT）の `references/slop-catalog.md` と `SKILL.md` を参考に、explainer 向けに短く書き直した。文を直す作業そのものを頼まれたときは、yomiyasu を使う。

## 冗長さの点検

書き終えたら、1 節ずつ次を確かめる。

1. ペルソナの「既に知っていること」に載っていることを説明していないか。載っていれば削る。
2. この節を消したら、理解度チェックのどれかが答えられなくなるか。ならないなら消す。
3. 例は、その節の主張に必要な最小の大きさか。
